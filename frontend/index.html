El problema

Las facturas eléctricas suben, pero casi nadie sabe qué hábito específico las infla: ¿el horario de uso, la cantidad de equipos, el tipo de vivienda? Sin esa visibilidad, no hay forma de decidir qué cambiar.

Nuestra respuesta

Un modelo entrenado clasifica el perfil energético en Eficiente, Moderado o Ineficiente, explica por qué con recomendaciones puntuales y traduce todo a un costo mensual estimado, en una sola llamada de API.

Arquitectura

De la lectura del medidor a la recomendación

Tres etapas conectadas, cada una con una responsabilidad clara — el mismo recorrido que sigue un dato real dentro del sistema.

01 — Ciencia de datos

  • EDA y limpieza sobre datos simulados/reales
  • Regresión Logística y Random Forest
  • Modelo serializado, servido vía FastAPI

02 — Backend API

  • Spring Boot 4.1 + Java 21, con TDD
  • Validación de entrada y manejo de errores
  • Auth JWT, historial e import CSV masivo

03 — OCI

  • Compute Ampere A1 (ARM), Docker Compose
  • MySQL HeatWave para persistencia
  • HTTPS propio vía Nginx + Let's Encrypt

Diferencial frente a otros equipos

No es un notebook. Es un sistema desplegado.

La consigna es la misma para todos los equipos del hackathon — esto es lo que hicimos con ella.

API en producción, no una demo local

HTTPS con dominio propio (appenergia.duckdns.org), corriendo 24/7 sobre OCI Compute Ampere A1.

Persistencia real

Migración completa a MySQL HeatWave en OCI, con historial de análisis consultable, no solo la respuesta puntual del endpoint.

Seguridad desde el diseño

Autenticación JWT y Spring Security protegiendo los endpoints, construido con TDD desde el primer commit.

Operable a escala

Importación masiva por CSV para analizar múltiples lecturas de consumo en una sola carga, no solo un registro a la vez.
